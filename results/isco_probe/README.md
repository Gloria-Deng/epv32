# EPV 侧整程序逐条轨迹比对探针（未认证；两次读数，中间修掉一条模型缺陷）

被 `三方评审/EPV32_逐目录评分与优化建议_20260925_1230.md` 的 P2-3 触发。
评审写的修法是「给 `tb/golden/epv_iss.py` 加 `LVB`/`SVB`」——实测错的，
模型早就实现了。真缺口当时有两条，一条是比对器只吃 ISA 的 `.S` 套件（已接上），
另一条到这一轮才现形：**模型自己的 EPV 解码比核严**（附件 A 台账第 23 条）。

`flow/iss_compare_epv.py` 把这件事接上了：同一份 ELF 喂 Verilator 与黄金模型，
比 R 线 (pc, rd, wdata) 与 S 线 (addr, wdata, be)，并按 `rtl/epv32_defs.vh`
现场解码「被比到的到底是哪几条扩展」。产物带 `_epvisco` 后缀，不碰认证归档。

**逐例读数不在这里抄**：本目录 `epv.json` 是那一趟的原样产物（`rows[]` 里有
`rtl_commits`、`iss_commits`、`iss_stop`、`reg_divergence_index`、
`reg_divergence_is_device_read`、`device_reads_total` 五个键），抄一份到这份
README 里就会漂——上一版确实漂了：它把四条程序的 `iss_stop` 全写成 max_steps，
而那是**修前**的读数，修后那一条已被同名覆盖掉，包内没有留副本（这本身记成
下面第 4 条）。

**测到的（截至本轮，四条程序）**
1. 模型侧不再死于步数耗尽：四条里三条跑到程序自己写的提交码，剩下 `nn_net` 仍是
   max_steps。修之前四条全是 max_steps。
2. 三条的首次分歧落在设备状态口那条 `lw` 上（核读 0 / 模型读 1，`uart` 那一路），
   轮询次数由该值决定，之后所有退休整体错位——这是模型头 quirk 15 那一条，
   本轮之后它不再是唯一障碍。
3. `nn_bench` 前进到一条**非设备读**的分歧：同一条 pc、同一个目的寄存器，核侧给
   一个非零值而模型给 0。**本轮没有定性**，也不给它起名字（附件 A 第 22 条的教训：
   先起名字会撤掉本来站得住的数）。要定它，得把两侧那一条的机器码与访存序列并排打出来。
4. 流程缺陷：探针用固定文件名覆盖自己的归档，所以修前那一次的读数没有留下副本。
   与包内"红件按 UTC 时间戳留一份"的规矩不一致；修法很小（落盘路径带修/修后标记），
   但它不改任何对外结论，本轮没做。

**这一格怎么算**：仍未收口。正文 5.5 第②条已从「EPV 侧仍未接」改成
「仍未收口（A.26）」，与本目录一致。本探针**不进矩阵、不出判决**，归档放在
`results/isco_probe/` 而不是 `results/isco/`——
`flow/check_deliverable_consistency.py` 的 `epv_trace` 规则原先只看
「isco 里有没有含 EPV 用例的归档」，一份跑失败的归档会把正确的「未做」判成过期；
该规则已改为读归档自己的判决（`all_agree` 且两个投影的 n_agree 都等于 n_tests）。

**什么能翻这一格**：两件事各自独立，都不小。
(a) 给模型的 UART/TIMER 加与 RTL 同宽的周期模型（发送移位器按 `uart_div` 递减、
busy 何时清），或改用不轮询设备的 EPV 比对用例；(b) 先定性上面第 3 条那条非设备读
分歧。两者都动到被当门禁键的源码（`tb/golden/epv_iss.py` 的哈希记在 isco 归档里），
⇒ 都要整链换代复认证。本轮已经付过一次这个代价：修解码之后
`python flow/run_all.py isco_trace` 复跑，三套件 66 个程序、14,700 条退休处分叉
比对仍然 diverging 为空，模型自检 356 → 365 条全过。

**复跑**：`python flow/iss_compare_epv.py`（约 40 s）；自检 `--selftest`。
